# HTKPA Reverse Engineering — Stage 19: native input FIR banks and real-probe checkpoint

**2026-10-12. Research-only. Actual initial A/B from native WAV: NOT COMPUTED.**

## Scope and strict evidence separation

Stage 18 demonstrated the **tail** of `0x1800BC6B0` once intermediate spectral arrays already exist. This stage follows the native audio path upstream from `0x1800BC6B0` and extracts its concrete **50-coefficient first FIR banks** from the original `5868USB.dll`. We also correct an erroneous historical claim about the native spectrum-window stride.

- **Binary proof:** Original Windows Sonicake Manager `5868USB.dll`, SHA-256 `fa8b3613a75de69deb49a9e72dce453312e4814a5c99bb6ea2e8a9e80debd5fa`, loaded as *bytes only*. We never execute the binary or connect to the pedal.
- **Independent source waveforms:** Original user-provided paired Manager-capture archives, one for JCM800 2203 Crunch and one for SC20 Full Rig. Their PCM16 stereo WAVs, both with identical channels, have matching 70-second 44.1-kHz input DI but distinct 70-second 48-kHz model outputs. Neither vendor CLO coefficient vector was accessed to compute any sound or filter. Reference CLO hashes are used *only* in separate test identity checks.
- **Numerical checkpoint:** The recovered **44.1-kHz 50-tap filter** was applied mathematically by *causal reference convolution* to the identical raw 44.1-kHz DI WAV. This is a grounded isolated operation, **NOT** proof that the Windows Manager consumed the unresampled raw DI or that the full native `0x1800B5A30` partitioned convolution is bit-identical. All subsequent IIR/saturator/STFT passes are deliberately excluded; the output is not native HTKPA A/B and not intended for listening.

## Native 50-tap sample-rate branches

The assembler in `0x1800BC6B0` checks exact float32 sample rates at:

- `0x1800BC739`: 44,100 Hz (`0x18024CDF0`) — starts table load `0x1800BC753`.
- `0x1800BC7EF`: 48,000 Hz (`0x18024CDF4`) — starts table load `0x1800BC802`.
- `0x1800BC89E`: 96,000 Hz (`0x18024CDF8`) — starts table load `0x1800BC8B1`.

Each branch loads **twelve SIMD float32 vectors** of four entries each, then **two trailing float32s**, reconstructing precisely 50 coefficients in order. All 42 referenced read addresses are independently matched to the proper disassembly branch and their bytes decoded directly from the PE (no fitting). At `0x1800BC94D`, native code passes the 50-entry stack array as `rdx`, sets `r8d=0x32` at `0x1800BC95A`, and calls the shared partitioned convolution helper `0x1800B5A30` at `0x1800BC96D`, with caller audio in `r9` and destination in the fifth Win64 argument. Its body `0x1800B5A30` calls the FFT-convolution helper `0x1800C0F60` in 64-sample blocks; its exact native float32 accumulation and end-of-buffer behavior have not been ported.

| Native bank | First three float32 taps | DC sum | Tap L2 |
| --- | --- | ---: | ---: |
| 44.1 kHz | 2.368210, 3.574280, 3.095710 | −0.0868914 | 7.695335 |
| 48 kHz | 2.369809, 3.532199, 3.386006 | −0.0252041 | 8.024002 |
| 96 kHz | 2.369809, 3.144882, 3.532199 | −0.9660231 | 11.273363 |

The full 50-tap values are **not hard-coded** into this research package: the verifier extracts all values directly from the user's local SHA-pinned DLL, making the analysis auditable while avoiding distribution of the vendor's arrays. The chart `initial_50tap_banks.png` plots their theoretical frequency responses.

## Source-grounded audio process, not yet independently complete

The native call and control flow is:

`0x1800BC6B0` → select 50-tap table → `0x1800B5A30` convolution → **first biquad** → `0x1800BE700` nonlinear saturator → **second biquad** → `0x1800B82B0` spectral comparison → Stage-18 two Gaussians / spectral floor / A/B quotient.

The first recursive section's state appears at `context+0x20/+0x28/+0x30`, with coefficients at `context+0x232D8…0x232F8`. The second section uses `context+0x20C98/+0x20CA0/+0x20CA8` and coefficients `context+0x23300…0x23320`. Both are consistent with the direct-form-II state equation:

`w[n] = 1000*x[n] − a1*w[n−1] − a2*w[n−2]`

`y[n] = 0.001*float32(b0*w[n] + b1*w[n−1] + b2*w[n−2])`

The code includes an intermediate float32 round-trip on the numerator before multiplying by 0.001. The original coefficients are computed by an *earlier initialization function* at `0x1800BFF17…0x1800C0216` using the context sample rate, then selected at `0x1800BEC36…0x1800BED00`. **We have located this initializer, but not reconstructed all its coefficients and edge cases**, so we deliberately do not emit a fake second-order-filter output. The nonlinear function `0x1800BE700` calls `0x180028690` with four model-dependent fitted gains, themselves generated by `0x1800BDBE0` from the audio before A/B construction.

### STFT hop correction to Stage 10

At `0x1800B8373` the analysis helper loads the **window/sample length** into `r14d`. At `0x1800B83EA…0x1800B83FB`, it computes:

`hop_samples = trunc(0.5 * window_length_samples)`.

Thus the historical statement *“half-second frame hop”* in Stage 10 was **incorrect**. This is a **50%-window hop**, not a fixed 0.5-second interval. When window length happens to be 4,800 at 48 kHz, it implies a 2,400-sample/0.05-second hop. This finding is based on *the actual source register*, not an STFT library default. Exact frame-end handling and native transform normalization still require validation. An erratum is separately appended to the Stage-10 repository document.

| --- | --- | --- | --- |
| 2203 Crunch | 44,100 Hz, 70 s | 48,000 Hz, 70 s | Yes |
| SC20 Full Rig | 44,100 Hz, 70 s | 48,000 Hz, 70 s | Yes |

SHA-256 of the byte-identical DI WAV in **both** archives: `9bb6c1b136dfbeb7538a6060499d98c89342b76ec568b76836e36ab98b29aa1a`. The 2203 output RMS ≈0.03403 and SC20 output RMS ≈0.01028; the model outputs differ. (These are source waveform summaries, not fitted gains.)

An **isolated causal 50-tap convolution** at the raw DI's 44.1-kHz rate produces RMS ≈0.82734 and peak ≈8.962 before any nonlinear/IIR stages. **These numbers must NOT be compared directly to the vendor output RMS**, because gain, nonlinear and filter transformations are missing and native sample-rate conversion may choose a different table. The evidence JSON contains four region-specific RMS/peak summaries and the first eight output samples. It never contains full user audio, vendor FIR coefficients or the proprietary binary.
